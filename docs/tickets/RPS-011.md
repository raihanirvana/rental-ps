# RPS-011 — Pengaturan usaha dan reset demo

Status: **Selesai**

Prioritas: **P1**

Dependensi: RPS-008, RPS-010

## Tujuan dan cakupan

Implementasikan GET/PATCH settings dan POST demo reset beserta UI owner. Reset menjadi
cara mengulang presentasi tanpa mengganggu pengunjung lain atau memperpanjang sesi.

## Kriteria penerimaan

- [x] Nama/alamat/teks kontak contoh dapat dibaca sesi dan diubah owner dengan validasi;
  jam buka/horizon/durasi tetap sesuai PRD. Markup input ditampilkan sebagai teks.
- [x] Reset memerlukan konfirmasi; membatalkan konfirmasi tidak mengubah data.
- [x] Reset atomik mengembalikan pengaturan, empat unit, booking dan blok contoh,
  menghapus key lama dan menaikkan versi data workspace.
- [x] Workspace/sesi/role/expiry dipertahankan; workspace pengunjung lain tidak berubah.
- [x] Kegagalan seed saat reset rollback ke keadaan sebelum reset.
- [x] Reset tidak meninggalkan booking/blok yang mengacu ke unit yang sudah hilang.
- [x] UI mengosongkan pilihan/detail lama dan mengabaikan respons yang dimulai sebelum
  reset; tab lain melakukan revalidasi saat aktif kembali atau versi data berubah.
- [x] Customer 403; expiry/logout bersamaan tidak membuat workspace hidup kembali.
- [x] Batas data sementara dijelaskan tanpa mengklaim backup atau login produksi.

## Verifikasi tanpa unit test

Ubah data, buat booking/blok, lalu reset. Bandingkan snapshot database sebelum/sesudah,
workspace kedua, TTL dan key. Uji cancel dialog, kegagalan transaksi, dua tab, fetch detail
terlambat dan reset bersamaan booking. Catat urutan commit serta keadaan UI setelahnya.

Untuk implementasi, `npm run check` harus lolos. Gunakan database/port sementara bila
relevan, periksa kembali [PRD](../../PRD.md) dan [aturan proyek](../../AGENTS.md).
Kerjakan tiket ini saja; fitur tiket berikutnya tidak otomatis ikut dikerjakan.

### Perubahan

- `GET /api/settings` (semua peran di workspace sendiri) → `settings` (nama, alamat, teks kontak),
  `rules` jadwal tetap, `dataVersion`. `PATCH /api/settings` (owner): `businessName` 2–60,
  `address` 2–150, `contactNote` ≤200, tanpa karakter kontrol; field lain (jam buka, durasi, …) 400.
- `POST /api/demo/reset` (owner, body persis `{ "confirm": true }`): satu `BEGIN IMMEDIATE` via
  `withWorkspaceAccess` (sesi/peran/expiry diperiksa setelah kunci) → hapus `booking_requests`,
  `bookings`, `unit_blocks`, `units`, `business_settings` → `data_version + 1` → seed ulang relatif
  hari ini. Baris workspace (`created_at`, `expires_at`) dan sesi tidak disentuh.
- Header `X-Data-Version` pada setiap respons API bersesi. Client: `onDataVersion` di `api.js`;
  `useDataVersionWatch` memvalidasi sesi saat versi berbeda, tab `focus`/`visibilitychange`;
  kunci halaman (`App.jsx`) memuat `dataVersion` sehingga halaman di-mount ulang setelah reset
  (pilihan, dialog, detail dan request yang berjalan dibuang/di-abort).
- UI `/pemilik/pengaturan` (`pages/SettingsPage.jsx`, `components/settings/*`): form identitas,
  pratinjau teks, aturan jadwal tetap, panel reset dengan dialog konfirmasi dan penjelasan data
  sementara (12 jam, bisa hilang, tanpa backup, bukan login produksi).
- `textarea` kini mewarisi font aplikasi. `DestinationPage`/`page-content.js` dihapus karena semua
  halaman sudah diimplementasikan.

### Batasan

- Tab lain tidak di-polling: data lama (termasuk respons yang dimulai sebelum reset dan tiba
  sesudahnya) bisa tampil sampai tab aktif kembali atau request berikutnya membawa versi baru.
  Di tab yang melakukan reset, halaman langsung di-mount ulang.
- Tab dalam satu browser berbagi satu sesi; ganti peran di satu tab berlaku untuk semua tab.
- Uji "workspace dihapus saat menunggu kunci" pertama kali memakai sqlite3 CLI tanpa
  `foreign_keys=ON` sehingga meninggalkan baris yatim buatan harness di DB uji; diulang dengan
  FK aktif dan hasilnya bersih (aplikasi selalu mengaktifkan FK).
- Hanya Chromium; Firefox/Safari dan pembaca layar sungguhan belum diuji.
