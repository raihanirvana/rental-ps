# RPS-007 — Alur memilih slot dan konfirmasi booking

Status: **Selesai**

Prioritas: **P0**

Dependensi: RPS-005, RPS-006

## Tujuan dan cakupan

Bangun alur pelanggan memilih unit/tanggal/durasi/jam, mengisi data dan mengonfirmasi
booking. Gunakan availability dan hasil server; jangan membangun kalender dengan data palsu.

## Kriteria penerimaan

- [x] Unit dan tarif mudah dibandingkan; tanggal/horizon dan durasi mengikuti PRD.
- [x] Slot membedakan tersedia, terisi, diblokir dan sudah lewat tanpa warna saja.
- [x] Pilihan unit/tanggal/durasi baru membatalkan hasil fetch lama; respons terlambat
  tidak menimpa pilihan terbaru. Tidak bisa submit hasil slot yang belum selesai dimuat.
- [x] Ringkasan memuat unit, waktu WIB, durasi dan quote; hasil akhir memakai total server.
- [x] Form berlabel, nomor opsional, anjuran memakai data contoh, serta field error server.
- [x] Submit dinonaktifkan saat berlangsung. Retry payload sama mempertahankan key;
  input booking berubah membuat key baru. Timeout tidak otomatis membuat request baru.
- [x] Konflik 409 menjaga isian dan menyegarkan slot; loading/empty/error/retry jelas.
- [x] Sukses menampilkan nomor reservasi, snapshot dan Bayar di tempat, tanpa label lunas.
- [x] Navigasi/reset sesi tidak menampilkan response booking dari sesi sebelumnya.

## Verifikasi tanpa unit test

Coba alur D+1 PS5 A 19.00 selama 120 menit: total Rp50.000. Simulasikan koneksi lambat,
request gagal/timeout, pergantian tanggal cepat dan slot direbut request kedua. Periksa
keyboard, ponsel, serta database bahwa klik ganda/retry hanya membuat satu booking.

Untuk implementasi, `npm run check` harus lolos. Gunakan database/port sementara bila
relevan, periksa kembali [PRD](../../PRD.md) dan [aturan proyek](../../AGENTS.md).
Kerjakan tiket ini saja; fitur tiket berikutnya tidak otomatis ikut dikerjakan.

### Perubahan

- `GET /api/catalog` kini juga mengirim `serverDate` dan `bookableDates` (tambahan, tidak
  mengubah field lama) agar tanggal default/min/max memakai server, bukan jam perangkat.
- Halaman `/booking` (`pages/BookingPage.jsx`, `components/booking/*`): pilih unit (radio,
  tarif per jam), tanggal (min/max server), durasi 1/2/3 jam, grid slot dari
  `GET /api/availability` dengan alasan teks, ringkasan (tanggal, jam WIB, durasi, tarif,
  perkiraan dari `quote` server), form nama + HP opsional, konfirmasi dari respons server.
- `useAvailability`: key per unit/tanggal/durasi, fetch lama di-abort dan responsnya
  diabaikan; tombol lanjut/submit hanya aktif untuk slot dari hasil yang sudah dimuat.
- `useBookingSubmit` + `lib/idempotency.js`: key dipakai ulang selama isi booking sama,
  key baru bila unit/jam/durasi/nama/HP berubah; guard klik ganda; batas tunggu 15 dtk tanpa
  retry otomatis; 409/400 jadwal → kembali ke langkah jadwal, slot disegarkan, isian tetap;
  error field server ditampilkan di field; respons setelah halaman ditinggalkan diabaikan.
- Halaman di-mount ulang per ruang demo + sesi + peran (`App.jsx`), sehingga respons
  booking dari sesi sebelumnya tidak tampil. Pilihan jadwal dikunci selama menyimpan.
- `styles/booking.css`, fokus heading programatik tanpa outline, DESIGN.md mencatat perbedaan.

### Batasan

- Blok sehari penuh untuk uji empty state dimasukkan langsung ke DB (RPS-010 belum ada).
- Batasan awal tentang perubahan harga sudah diperbaiki dalam review: quoteId dibandingkan
  di dalam transaksi, 409 sebelum insert, harga ditinjau ulang sebelum konfirmasi kedua.
  Tarif diubah langsung pada DB sementara karena UI pengaturan unit belum dibuat.
- Hanya Chromium; Firefox/Safari dan pembaca layar sungguhan belum diuji. Screenshot
  full-page Chromium menggambar skip link fixed di posisi scroll; diperiksa tidak fokus.

## Review lanjutan RPS-006–007

Respons 200 JSON rusak dan body timeout kini menjadi error yang bisa dicoba ulang, bukan
konfirmasi null. Quote ID mencegah penerimaan tarif baru tanpa tinjauan ulang, termasuk
saat tarif berubah oleh penulis lain ketika booking menunggu lock. Tarif ringkasan dan
pilihan unit mengikuti availability terbaru. Retry tetap memakai key/payload yang sama,
termasuk quoteId; format hash legacy tanpa quoteId dipertahankan. Kontrol pada isian
pelanggan divalidasi sebelum normalisasi. Semua uji terkait lolos; lihat
[catatan review](../REVIEW-RPS-006-007.md).
