# RPS-005 — Booking atomik, detail dan pembatalan

Status: **Selesai**

Prioritas: **P0**

Dependensi: RPS-004

## Tujuan dan cakupan

Implementasikan POST booking, GET mine/detail dan POST cancel. Semua keputusan jadwal,
harga, snapshot dan hak akses menjadi tanggung jawab server. Tambahkan kontrak error API.

## Kriteria penerimaan

- [x] Input sesuai allowlist PRD; nama wajib, nomor opsional dan key divalidasi, field harga,
  workspace, role atau status dari client ditolak.
- [x] BEGIN IMMEDIATE melindungi pemeriksaan ulang sesi, replay key, unit, waktu,
  konflik, harga, INSERT booking dan penyimpanan key. Error selalu rollback.
- [x] Dua request berbeda pada slot bertabrakan menghasilkan satu 201 dan satu 409.
- [x] Key/payload sama mengembalikan booking sama dengan 200; key sama payload berbeda 409.
  Replay booking cancelled tidak menghidupkannya kembali.
- [x] Nomor reservasi unik; nama/jenis/tarif/total disimpan sebagai snapshot.
- [x] Mine hanya booking asal pengunjung workspace sendiri; seed hanya terlihat untuk owner.
  Detail yang tidak boleh dilihat mengembalikan 404. Daftar dibatasi/paginasi server.
- [x] Customer hanya membatalkan confirmed sebelum mulai; owner boleh membatalkan confirmed.
  Alasan/aktor/waktu tersimpan; pengulangan pembatalan identik tidak membuat efek baru.
- [x] Konflik status/slot 409, validasi 400 dengan fields, sesi 401 dan role 403;
  database busy ditangani terkendali, bukan membocorkan stack trace.

## Verifikasi tanpa unit test

Kirim dua request bersamaan pada port dan database sementara; hitung baris hasilnya.
Uji overlap sebagian, adjacency, retry key, perubahan payload, rollback, snapshot dan
pembatalan. Uji kedua role serta ID workspace lain. Catat bukti curl/SQL, tanpa unit test.

Untuk implementasi, `npm run check` harus lolos. Gunakan database/port sementara bila
relevan, periksa kembali [PRD](../../PRD.md) dan [aturan proyek](../../AGENTS.md).
Kerjakan tiket ini saja; fitur tiket berikutnya tidak otomatis ikut dikerjakan.

### Perubahan

- `POST /api/bookings` (customer/owner): allowlist `unitId`, `date`, `startTime`,
  `durationMinutes` (angka 60/120/180), `customerName` (2–60, tanpa karakter kontrol),
  `phone` opsional (spasi/tanda hubung dibuang, 8–15 digit, `+` opsional) dan
  `idempotencyKey`. Field lain (harga, total, status, workspace, role, …) → 400 per field.
- Satu `BEGIN IMMEDIATE` via `withWorkspaceAccess`: sesi diperiksa ulang → replay key
  (hash payload tanpa key) → horizon/grid/jam buka → unit (404 asing, 409 nonaktif) →
  lead time (400 `START_TOO_SOON`) → konflik booking/blok (409 `SLOT_UNAVAILABLE`) →
  harga server → nomor `SP-XXXXXX` unik → INSERT booking + `booking_requests`.
  201 baru, 200 replay (status terkini), 409 `IDEMPOTENCY_CONFLICT` bila payload beda.
- `GET /api/bookings/mine?view=upcoming|finished|cancelled&limit≤50&offset`: hanya
  `source=visitor` workspace sendiri, dengan `total`, paginasi dan `timeState`
  (`upcoming`/`ongoing`/`ended`). Didaftarkan sebelum `/:id`.
- `GET /api/bookings/:id`: customer hanya booking pengunjung; seed/workspace lain/ID asing 404.
  Owner semua booking workspace sendiri. Detail berisi snapshot dan `payment: pay_at_venue`.
- `POST /api/bookings/:id/cancel` body opsional `{ reason }` (≤200): customer hanya confirmed
  sebelum mulai; owner semua confirmed termasuk berlangsung. Simpan aktor/waktu/alasan.
  Ulang dengan alasan sama → 200 `changed: false`; alasan beda → 409; completed → 409.
- Error: trigger database (`SCHEDULE_CONFLICT`, dll.) dipetakan ke 409; SQLITE_BUSY → 503
  `DATABASE_BUSY` + `Retry-After` (penanganan busy sudah ada di `errors.js`).
- File: `validation/booking-validation.js`, `booking-query-validation.js`,
  `services/booking-service.js`, `booking-slot.js`, `booking-cancel-service.js`,
  `booking-query-service.js`, `booking-view.js`, `booking-access.js`, `routes/bookings.js`,
  tambahan `repositories/booking-repository.js`.

### Temuan dan perbaikan selama uji

- `GET /bookings/mine?view=cancelled` sempat 500: `node:sqlite` menolak parameter bernama
  `$now` yang tidak dipakai filter cancelled. Diperbaiki (parameter hanya bila dipakai),
  ketiga view diuji ulang.

### Batasan

- Booking berlangsung, blok dan unit nonaktif untuk uji dibuat langsung di database
  (pengelolaan unit/blok di RPS-010).
- Kedua peran demo boleh membuat/membaca booking, jadi 403 tidak terjadi di endpoint ini;
  `requireRole` 403 sudah dibuktikan di RPS-003.
- Lead time 15 menit untuk booking memakai fungsi yang sama dengan availability
  (diuji di RPS-004); pada jam uji tidak ada slot grid di dalam jendela 15 menit.
- Paginasi memakai limit/offset; cukup untuk demo, tidak stabil bila data berubah antar halaman.
